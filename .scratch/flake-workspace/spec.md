# flake 数据规格：把 CLI 子集从 flake 里移出来，由根清单 / lock 派生

Status: ready-for-agent
Labels: ready-for-agent

> 由 2026-10-18 的十二问 grilling 坍缩而成（架构评审候选 4「把 flake.nix 里 2281 行手抄的 CLI 工作区移出 flake」）。
> 结构取舍**不新增 ADR**：`docs/adr/` 只记领域规则（ADR-0001..0004）；构建侧的决定沿用既有惯例，记在本规格、三张票与代码注释里。
> 冻结的既有决定：ticket 02 的 Q5——CLI 与 GUI 是两个 workspace、两份 lock——**不重开**。本规格只解决「第二份 workspace 的数据必须内联在 flake 里手抄」这一半。
> 前置：候选 1（`Runner`，ADR-0003，`651b48e`）与候选 2（`Readiness` + 写侧边界，ADR-0004，`11e8a48`）已完成。
> 可感知的行为变化：**无**。一次性构建变化见 §7（CLI 第三方依赖版本与根 lock 统一、`cliCargoDeps` 哈希与依赖缓存输出改变）；根 `Cargo.lock` 与 GUI 侧不动。

## Problem Statement

flake 的 interface 很小（`nix build .`、`.#plainly`、`nix develop`、`.#default`、`nix run`），实现却是 2754 行，其中 **2281 行（82.8%）是数据**：手写的 `cliManifest`（29 行）与手写的 `cliLock`（2251 行）。

- **它是第二份真源，而且已经漂移。** flake 注释自己写着「This is a second source of truth and it is hand-synced」：根 `Cargo.toml` 的改动不会到达它。实测今天两份数据已经不一致——根 lock 540 个包，剪出 CLI 闭包是 237 个；flake 里的 `cliLock` 是 236 个，其中 15 个共享包的版本不同（`time` 根里 0.3.55 / 字面量里 0.3.45，`cc` 1.6.0 / 1.7.0，`syn`、`toml_edit`、`wasm-bindgen*`、`zeroize` 等），且字面量里缺一个根闭包中的 `futures-sink`。没有测试断言它们同步，唯一发现漂移的信号是 vendor hash：`nix build` 报出它拿到的哈希，然后人去改。
- **一次依赖变化要动 6 个触点 / 3 个文件**：根 `Cargo.toml`、根 `Cargo.lock`、两份 lock、两个 vendor hash、`cliManifest`；生成 `cliLock` 还得把 manifest 拷进一个 checkout、`cargo generate-lockfile`、再把 2251 行粘回 flake。ticket 02 的 Q5 记录过这个成本（`runner/tickets/05` 的 Comments 里也留了一次实例：给 CLI 补一个 dev-dependency 就要改 flake 字面量）。
- **守卫脚本被这份内联数据绑架。** `scripts/check-incremental-build.sh --self-test` 需要「改 CLI 的 lock 来源」来证明 CLI 那条检查还活着，而 CLI 的 lock 来源藏在 flake 源码里，于是脚本用 Python 切片在 `flake.nix` 里找 `cliLock = pkgs.writeText ...` 的字符串（`scripts/check-incremental-build.sh:67-75`）。数据搬出 flake，这段才能删掉。
- **同一类事实被写两遍。** `.scratch/plainly/spec.md` §14 写着「`rust-version` 下限同步在 `Cargo.toml` 与 flake 内的 `cliManifest` 两处」；flake 的工具链注释也复述了同一句。README 的「两个包」叙述不需要变。

这不是「flake 里不该有数据」的教条：数据必须有一份，问题在于它的**owner**。CLI 的 workspace 是根 workspace 的一个投影（两个 crate 的子集 + 它们的依赖子集），这个投影应该由生成器从根清单 / lock 算出来，而不是由人在 2251 行里手工维持。

## Solution

**CLI 子集的 manifest 与 lock 作为生成物进仓库，flake 只引用。**

- 新增 `nix/cli-workspace/{Cargo.toml,Cargo.lock}`：由 `scripts/generate-cli-workspace.sh` 从根 `Cargo.toml` / `Cargo.lock` 派生，manifest 一步在求值之外算出，lock 一步交给 cargo 自己规范化；两个文件都提交、可审、带「生成，勿手改」的头。
- `flake.nix` 删掉 `cliManifest` / `cliLock` 两个 `let` 绑定与那段「手同步 / 粘贴」的注释，2754 行回到约 470 行；`cliSource` 改为 `cp ${./nix/cli-workspace/Cargo.toml}` / `Cargo.lock`。**flake 里不再有 `[[package]]`、手写依赖版本、手写 lock。**
- 新增 `scripts/check-cli-workspace.sh`：纯 `python3`、离线、不需要 nix/cargo 的同步守卫——manifest 是否等于派生值、committed lock 的每个 `(name, version)` 是否都在根 lock 里同名同版本、两个 crate 里所有 `workspace = true` 的依赖是否都被 manifest 覆盖。失败时打印重新生成的命令。
- 生成器与守卫的分工是**故意不对称**的：生成器需要 cargo（lock 只能由 cargo 的 resolver 产出），守卫**不需要** cargo（它只检查「生成物是否还同步于根清单 / lock」这一性质，在依赖变更、评审、升级 flake 输入后都能廉价重跑；`cargo --locked` 的严格性由 `nix build` 保证）。

为什么不是「求值时纯 Nix 派生」：已实测证伪（§8 与 Further Notes 有数字）。(1) Nix 2.34.8 没有 `builtins.toTOML`；(2) 更根本的是 `Cargo.lock` **不记录启用了哪些 feature**，从根 lock 剪出的 CLI 子集必然是对 CLI feature 集的过近似，`cargo metadata --locked` 会拒绝（要删未激活的包与依赖边），而 crane 默认 `--locked`，所以 `nix build` 会以同样的方式失败。这个规范化只能由 cargo 自己做。

## User Stories

### 维护者

1. 作为维护者，我改一个 CLI 依赖时只需要动根 `Cargo.toml` + 根 `Cargo.lock`（`cargo update`），跑一次生成器、提交两个生成文件，而不是在编辑器里连续两次手抄 lock。
2. 作为维护者，我给 `plainly-cli` 加一个依赖时，flake 里没有任何一行需要跟着改。
3. 作为维护者，我改 `rust-version` 时只改根 `Cargo.toml`，不再有一个「第二处」会漂移。
4. 作为维护者，我打开 flake.nix 时看到的是逻辑（工具链、包、shell、app），不是 2251 行 lock。
5. 作为维护者，我在依赖变更后能离线跑一条命令，知道生成物是否已过期，而不必先 `nix build` 等它用哈希报错。
6. 作为维护者，我读 `nix/cli-workspace/Cargo.lock` 时看到的是普通 Cargo 文件，版本变化就是普通 diff，而不是一个藏在 Nix 字符串里的字面量。

### 评审者与 CI

7. 作为评审者，我能在 diff 里看见 CLI 依赖版本的真实变化（生成物提交后是可见的），而不是「flake 里某段哈希变了」。
8. 作为评审者，我知道守卫脚本不再需要在 flake 源码里找字符串（`check-incremental-build.sh` 的 Python 切片消失）。
9. 作为 CI 维护者，我知道这次不改 CI（CI 继续只跑 core / cli 的 cargo 测试与 clippy）；守卫是手动脚本，与 `check-flake-packages.sh` / `check-incremental-build.sh` 同一类。

### 打包与闭包

10. 作为在没有图形栈的机器上构建 CLI 的人，我的构建闭包里仍然只有 CLI 的 vendor 子集，不会因为这次改动拖进根 workspace 的 540 个 crate 源码。
11. 作为 GUI 用户，这次改动不影响 GUI 的构建产物：根 `Cargo.lock` 不动，`guiCargoDeps` 的哈希与依赖缓存不变。
12. 作为维护者，「CLI 与 GUI 是两个 workspace、两份 lock」这条决定仍然成立；本规格只换掉第二份 lock 的**存放与产生方式**。

### 构建的正确性

13. 作为构建者，我依赖 `cargo --locked` 仍然是真的：生成的 lock 必须被 cargo 接受，而不是靠 `--offline` + 重写蒙混过关。
14. 作为未来的读者，我能在规格里找到「为什么这件事不能纯 Nix 做」的实测证据，而不是重新试一遍。

## Implementation Decisions

### 1. 生成物的位置与形状

- 新目录 `nix/cli-workspace/`，两个文件：
  - `Cargo.toml`：第一行注释 `# Generated by scripts/generate-cli-workspace.sh from the root Cargo.toml. Do not edit.`，随后
    - `[workspace]`：`resolver` 从根清单原样取；`members = ["crates/plainly-core", "crates/plainly-cli"]`（两项，顺序固定）；
    - `[workspace.package]`：根清单现有的 4 个字段原样复制（`version` / `edition` / `rust-version` / `license`；根清单将来新增的字段也自动带上）；
    - `[workspace.dependencies]`：**只保留两个 crate 实际以 `workspace = true` 继承的条目**（今天 11 项：`plainly-core`、`clap`、`keyring`、`object`、`rusqlite`、`serde`、`serde_json`、`sha2`、`thiserror`、`toml_edit`、`ureq`）。根清单里的 GUI 专用项（`gtk`、`gtk-layer-shell`、`wayland-client`、`wl-clipboard-rs`）不出现——即使 cargo 会忽略未使用的 workspace 依赖，flake 与生成物里也不该出现 GTK 的名字。顺带：今天手抄清单里的 `async-channel` 实际没有任何 crate 使用，派生时自然消失（无解析影响）。
    - 依赖条目的格式统一为内联表 `name = { version = "4", features = ["derive"] }` 或 `name = "2"`，键按根清单顺序；`default-features = false` 等布尔字段照抄。
  - `Cargo.lock`：**由 cargo 写出的**普通 lock（保留 cargo 自己的 `# This file is automatically @generated by Cargo.` 头，不再额外加注释），v4，236 个包（数量由 cargo 决定，不写死）。
- 不放在 `crates/` 下：那会让人以为它是 workspace 成员；`nix/` 是构建数据的位置。

### 2. 生成器 `scripts/generate-cli-workspace.sh`

bash 脚本 + 内联 `python3`（`tomllib`），与 `check-incremental-build.sh` 同一种 house style；投影规则本身（members、继承依赖、manifest 的渲染）在 `scripts/cli_workspace.py` 里，守卫共用同一份，不各写一遍。步骤：

1. **派生 manifest**：读根 `Cargo.toml` 与两个 crate 的 `Cargo.toml`；对 `[dependencies]` / `[dev-dependencies]` / `[build-dependencies]` 里**所有** `{ workspace = true }` 的名字取并集，套用 §1 的格式写成 manifest。
2. **剪种子 lock**：读根 `Cargo.lock`，从 `plainly-core` / `plainly-cli` 出发按 `[[package]].dependencies` 求传递闭包（依赖串可能是 `"name"` 或 `"name version"`，当 lock 里有重名多版本时后者出现——今天根 lock 有 80 处），按根 lock 原顺序保留闭包内的 `[[package]]` 条目，写成种子 lock。**种子只是过近似**，不要求 cargo 接受。
3. **交给 cargo 规范化**：临时目录里写入派生 manifest + 种子 lock，`cp -r` 两个 crate（`plainly-panel` / `plainly-desktop` 从不复制），跑 `cargo metadata --offline --format-version 1`；离线失败（本机没有该 crate 的缓存）时回退到不带 `--offline` 的一次（并在 stderr 说明用到了网络）。cargo 会把种子修成它自己的解析结果：未激活的包与依赖边、版本消歧符都由它决定。**版本跟根 lock 走**：种子锁住了版本，cargo 只做规范化、不升级。
4. **写回** `nix/cli-workspace/{Cargo.toml,Cargo.lock}`，打印 `git diff --stat`；`--check` 模式只比较不写（供实现期与评审期用；守卫脚本本身不依赖它）。
5. 需要 `cargo`（`nix develop` 里的 1.99.1）：脚本开头不在 dev shell 时给出明确报错。首次运行需要网络或已有的 cargo 缓存（要读 236 个依赖 crate 的 manifest）；之后是毫秒级。
6. 失败时（cargo 拒绝、根 lock 里找不到成员或依赖、CLI 闭包为空、根清单声明了 crate 继承却缺失的依赖等）不写任何文件，exit 1 并保留临时目录路径。

**已验证的前提**（grilling 期在 `/tmp` 实测，cargo 1.99.1）：种子（237 包）→ `cargo metadata` → 236 包且 `cargo metadata --locked` 通过；与今天的 flake 字面量相比只有 15 个共享包版本不同（见 §7），包数都是 236。纯 Nix 求值路线的反例见 §8。

### 3. 守卫 `scripts/check-cli-workspace.sh`

bash + 内联 `python3`（投影规则与生成器共用 `scripts/cli_workspace.py`，导入时关掉字节码，不留下 `__pycache__`），**离线、不调用 nix 或 cargo**，因此比现有三个 check 都便宜。检查四项，**每项都能独立失败**，任一失败 exit 1 并打印 `bash scripts/generate-cli-workspace.sh`：

1. `nix/cli-workspace/Cargo.toml` 的**形状**与**依赖声明**是派生值：`resolver` / `members` / `[workspace.package]` 按 TOML 语义相等、没有多余的顶层节、每个继承依赖的声明值都等于根清单（比较 `tomllib` 解析后的结构，不比较格式）；依赖名的缺与多分别由第 3、4 条判，避免一个错误报三条 FAIL；
2. `nix/cli-workspace/Cargo.lock` 与根 `Cargo.lock` 一致：每个 `(name, version)` 都在根 lock 里同名同版本；包集不超出「根 lock 从两个 crate 出发的传递闭包」（闭包是过近似——cargo 会剪掉 GUI 激活而 CLI 不用的包，所以只要求 committed ⊆ 闭包）；锁内每条依赖边都能在锁里解析。这一条专门抓「根 lock 把共享依赖挪了版本、CLI lock 还是旧版本、但 `cargo --locked` 因为要求仍满足而放行」的漂移，以及「committed lock 缺包 / 超出包集」；
3. 两个 crate 的 manifest 里所有 `workspace = true` 的依赖名都出现在 committed manifest 的 `[workspace.dependencies]` 里（抓「加了依赖忘了生成」）；
4. 反向：committed manifest 的 `[workspace.dependencies]` 不出现两个 crate 都不用的名字（抓手改与误加）。

文档：`docs/manual-checks.md` §0 加一段（依赖变更后、升级 flake 输入后跑；只读、约 1 s；不装 Nix 也能跑）。**不改 CI**（评审候选 4 之外的范围冻结）；若将来要防合并前漂移，这个脚本可以一行加进 CI，因为它不装 Nix、不碰图形栈——留作后续，不在本规格内。

### 4. `flake.nix` 收口

- 删除 `cliManifest`（216–244 行）与 `cliLock`（245–2496 行）两个绑定，以及那段「second source of truth / 手同步 / 粘贴」的注释；在同一位置改写一段短注释：CLI workspace 的 manifest 与 lock 由 `scripts/generate-cli-workspace.sh` 从根 workspace 派生、提交在 `nix/cli-workspace/`、由 `scripts/check-cli-workspace.sh` 守同步；**保留**「为什么需要合成 workspace」的那半段理由（`libdbus-sys` 在沙箱里 panic、dev shell 里探测不到，ticket 02 的 Q5）。
- `cliSource`：`cp ${./nix/cli-workspace/Cargo.toml} $out/Cargo.toml`、`cp ${./nix/cli-workspace/Cargo.lock} $out/Cargo.lock`（其余不变）。
- `cliCargoDeps.hash` 更新一次（lock 内容变了，Nix 会报出新哈希；实现时把新旧值记进票）。
- 顶部工具链注释（40 行）与 §14 里「`rust-version` 同步在两处」的复述改成一处（根 `Cargo.toml`；CLI manifest 是派生的）。
- 对外 interface 完全不变：`packages`、`apps`、`devShells`、`formatter` 不动，`checks = { }` 保持为空（理由注释不动），不新增 flake 输出。

- `--self-test`：GUI 的控制项仍是「往根 `Cargo.lock` 追加一行」；CLI 的控制项改为「往 `nix/cli-workspace/Cargo.lock` 追加一行」；删掉 `flake.nix` 的 Python 切片（67–75 行）；两个 cache 都必须报失效才通过（语义不变）。

- `docs/manual-checks.md` 33–36 行的「（repo 的 `Cargo.lock` 与 flake 里的 `cliLock` 字面量）」改为「（repo 的 `Cargo.lock` 与 `nix/cli-workspace/Cargo.lock`）」。

### 7. 一次性构建变化（可见行为不变）

- CLI 的第三方依赖版本统一到根 lock 的解析（grilling 实测的 15 个包）：`cc` 1.6.0（原 1.7.0）、`js-sys` 0.3.100、`num-conv` 0.2.2、`smallvec` 1.16.2、`syn` 3.0.6、`time` 0.3.55、`time-core` 0.1.9、`time-macros` 0.2.32、`toml_edit` 0.25.15、`toml_parser` 1.1.4、`wasm-bindgen`（及 `-macro` / `-macro-support` / `-shared`）0.2.123、`zeroize` 1.9.0；包数仍 236。实现时以生成器在仓库上的实际输出为准，差异记进票。
- `cliCargoDeps` 的哈希与 `plainly-deps` 的依赖缓存输出改变 → 一次 CLI 依赖重建（分钟级）。
- 派生 manifest 少一个未使用的 `async-channel` 条目（无解析影响）。
- 根 `Cargo.lock` 不动 → `guiCargoDeps` 哈希不变、GUI 依赖缓存不变；`gui` 最终包因 `wholeSource` 多了 `nix/` 两个文件而重建一次（依赖缓存不动）。
- 产品行为、CLI 输出、退出码、store schema、Explanation 契约：全部不变。

### 8. 被拒绝的替代方案

- **纯 Nix 求值派生（不提交）**：不可行。实测：Nix 2.34.8 只有 `fromTOML`、没有 `toTOML`；更根本的是 `Cargo.lock` 不记录启用的 feature，剪出的子集必然过近似，`cargo metadata --locked` 报 `cannot update the lock file ... because --locked was passed`，cargo 要删 `futures-sink` 与 feature 未激活的边（`bitflags→serde_core`、`bytes→serde`、`futures-util→futures-io/futures-sink/memchr`、`indexmap→serde/serde_core`、`uuid→getrandom` 等），再补 80 处版本消歧符。crane 默认 `--locked`（`buildDepsOnly.nix:12`、`buildPackage.nix:14`），所以 `nix build` 会同样失败。纯 Nix 要做的是重写 cargo 的 resolver。
- **flake 内生成器派生（不提交、runCommand 里跑 cargo）**：可行但没有采纳。生成 exact lock 需要所有 CLI 依赖的 manifest，也就是把根 workspace 的 vendor（540 个 crate、本地 762MB 源码）变成 CLI 构建的输入，直接抵消候选 3 的成果（CLI 的 vendor 只有 236 个包、与 GUI 分开）和「没有图形栈的机器构建 CLI」的成本承诺。
- **只派生 manifest、保留手抄 `cliLock`**：半程。2281 行里 2251 行是 lock，留下它等于没解决；`--self-test` 的 Python 切片也留着。
- **改回单 workspace / 单 lock**：ticket 02 的 Q5 冻结（两份 vendor 不同，合并会让 GUI 依赖变化失效 CLI 的依赖缓存，也会把 GUI 的 vendor 拖进 CLI 包）。
- **用 `cargo generate-lockfile` 从依赖要求重新生成（不拿根 lock 当种子）**：版本会取到当时最新，与根 lock 分道扬镳，正是今天的漂移来源。
- **新增 ADR**：ADR 目录是领域规则（0001–0004）；构建侧决定按既有惯例记在 spec + 票 + 注释。

## Testing Decisions

本规格不改产品代码，没有新的 crate 级单测；「测试」是构建层面的判据，全部在票里记录实际输出：

- **生成器可复现**：在干净树上跑一次 `scripts/generate-cli-workspace.sh`，`git diff` 为空（给定根清单 / lock 与 cargo 1.99.1，输出确定）。
- **`cargo --locked` 仍然为真**：`nix build .#plainly` 的 checkPhase 走 `cargo test --locked`；它通过即证明提交的 manifest/lock 是 cargo 的 exact 解析，而不是靠放宽 `--locked` 蒙混。
- **闭包承诺**：`scripts/check-flake-packages.sh --no-build` 通过（CLI 闭包无 GTK/WebKit/Wayland/dbus、两个包闭包大小仍不同、面板 `env -i` 仍能起、CLI 无环境读 Passage 等既有断言）。
- **增量缓存仍然独立**：`scripts/check-incremental-build.sh` 正向通过（改 `.rs` 两个依赖输出不变）；`--self-test` 通过（根 `Cargo.lock` 与 `nix/cli-workspace/Cargo.lock` 各自让对应的依赖输出失效）。
- **新守卫的正反向**：正向在干净树上 exit 0；反向三个手工控制各自让它 exit 1——(a) 改根 `Cargo.lock` 里某个共享包的版本，(b) 改 committed manifest 删一个依赖，(c) committed manifest 加一个没人用的依赖；每次控制后 `git checkout` 恢复。
- **接口不变**：`nix develop -c cargo --version`、`nix build .#default`、`nix run .#plainly -- --version` 可用；`grep -c '^\[\[package\]\]' flake.nix` 为 0，`grep -n 'cliManifest\|cliLock' flake.nix` 为空，`wc -l flake.nix` ≤ 500。
- **不测**：真实注册表之外的网络行为、cargo 版本升级后的 lock 格式变化（那是候选 1 里既有 `incremental-build` 的职责）、`nix flake check`（仍为空）。
