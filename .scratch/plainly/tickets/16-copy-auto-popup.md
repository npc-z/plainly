# 16: 「复制自动弹」

**What to build:** 在支持的桌面上，我复制一段就自动弹出解释——默认关闭；不支持时开关灰着并告诉我为什么。

**Blocked by:** 12, 14

**Spec:** [spec.md](../spec.md) §12「复制自动弹」（含规格层补定的监听归属）

**Status:** done (2026-10-10)

- [x] 默认关；开启后由 `plainly-desktop` 持有监听循环（`--watch`，或主窗口保持运行），**默认路径下仍然没有常驻进程**
- [x] 只在具备 data-control 的桌面上可用；能力不足时设置里**灰掉**并附一行可操作说明（不隐藏）
- [x] 监听命中新 Passage 时的行为与键绑一致：面板复用、幂等命中缓存、`activate` 语义相同

- [x] 快速连续复制不会排队炸出多个面板或多次请求

## 落地形态

**监听在 `plainly-desktop` 里，是一个线程而不是第二个二进制**（`src/watch.rs`，约 1000 行含测试）：

| 文件 | 它是什么 |
| --- | --- |
| `src/watch.rs` | `Watch`：一个可测的状态机（`Observer` + `Clock` 两个注入点）、面板的 spawn、`Handle`（窗口用来停它，带停止原因） |
| `src/clipboard.rs` | 监听读剪贴板的那一半：`Changes`，每次等待一条 data-control 连接 + 一个守时线程，水位与 deadline |
| `src/copy.rs` | 原来 `clipboard.rs` 里「写剪贴板」的那一半，原样搬过来 |
| `src/window.rs` | `Mode::{Window,Watch}`、`Watching`（监听的生命周期：一个交接该起、该留还是该停）、窗口退出时收尸 |
| `src/single.rs` | 交接那句话从 `activate` 变成 `activate --watch|--nowatch` |

**监听只做一件事：数静默。** 拿到一个文本 reading 就把它当作「手上这段」，然后一片一片地等（`POLL = 50ms`）；
每一片有新 copy 就把窗口清零，连续 `SETTLE = 250ms` 没有新 copy 才 spawn 一次
`plainly-panel --clipboard`。面板自己再读一次剪贴板、自己判定敏感、自己查缓存、自己复用已有窗口——所以
**自动触发与键绑是同一条路径**，不是两份会各自漂移的实现（spec §11、§12）。

三个只在实现时才被迫想清楚的点：

- **「第一次读到的东西」不是 copy**：监听启动时剪贴板里已有的那段是 arm，只作为比较基准，永远不为它弹面板。
- **「应用重新声明同一个 offer」也不是 copy**：`armed` 这个位只由「新 copy」抬起（reading 变了，或者
  reading 没变但上一个面板已经弹过又关掉了）。所以同一段文字在面板弹过之后**再复制一次**会再弹（那是 copy），
  而剪贴板自己重复声明同一个 offer 不会（`clipboard.rs` 的 `types` 参与比较，测试写了这条）。
- **quit 与 quiet 必须分开**：`Observer` 把「剪贴板没有新东西」和「监听本身结束了」分成两个问题
  （`next` 返回 `None` 与 `over()`）。合成一个的话，人停手 250ms 就会被当成监听结束。

**谁拉起监听：键绑或桌面自启动，不是窗口。** 窗口写出 `copy_auto_popup = true` 时**不会** spawn 任何东西——
那会绕过「默认路径下没有东西需要常驻」。监听的停止有两条路，都不靠信号：`Watch::enabled()` 每轮重读配置，
开关关掉就退出；交接语句里的 `--watch|--nowatch` 说清这次启动是不是 watcher，后来的**不带 `--watch`** 的启动
会让监听退出（面板的 ⤢、桌面快捷方式都走这条）。`--nowatch` 只是那句话在 socket 上的写法，**不是命令行参数**。

**`--watch` 是对窗口的请求，不只是它自己启动时的模式**：窗口已经开着时再跑一次 `plainly-desktop --watch`，
交接到达的那个窗口会**开始**监听（`Watching::ask`），所以「用 `--watch` 打开它」和「让它开始监听」是同一件事。
反过来，不带 `--watch` 的启动会停掉正在跑的监听——否则按一次 `--watch` 就永远停不下来了。这个判断是一个纯值
（`Watching`：配置路径 + 一个 `Handle` slot + 注入的 `start`），所以有测试；**两个真实进程之间**的交接仍然
只有真机能验，归 17。

**重复代码是边界决定的，不是省事**：`plainly-desktop` 的 data-control 读取与 `plainly-panel` 的那份重复
（约 50 行）。core 不能依赖 Wayland（要留给 macOS / Windows），panel 是只有 bin 的 crate，消重要么再开一个
共享 crate、要么让 desktop 依赖 panel——两条都比这五十行贵。重复的是**读**，判据仍然只有一处
（`plainly_core::clipboard`）：监听比较的是整条 reading（原文 + types），它唯一不碰的判据是
「这段算不算敏感」——那是 core 的，面板执行。

**`Changes` 一次等待一条连接：先读水位，再在同一条连接上等到真的变了或 deadline**：`wl-clipboard-rs`
的 `Watcher` 有两条会咬人的性质——第一，**它建好之后的第一次 `next_event` 报的是「剪贴板上现在是什么」**
（水位，不是事件；crate 自己的 rustdoc 与 `watch_initial_changed` 测试都写着）；第二，被
`CancelHandle::cancel()` 取消过的 watcher 是**永久**结束的（它 `wait` 里 poll 的那个管道一直可读）。所以：

- 一个 watcher 不能跨等待复用，否则第一片之后的所有复制全都看不见（早期版本正是这样，而且在空转重读
  `config.toml`——真机上才发现，假的 `Observer` 挡不住这类错误）；
- 水位也不能当成「变了」返回。`Changes` 读掉水位后**留在同一条连接上继续等**：水位等于手上那段就等到真变了
  或者 deadline 到了。把水位当报告返回，会让每一次等待都「有东西」，于是永远没有静默、settle 窗口永远攒不满，
  静止的剪贴板上一个面板都不会弹（第四轮 review 抓到的正是这条）。

合成的结果是干净的：一次 `quiet(deadline)` 要么是一条**真正的新报告**，要么是静默（deadline 到了），
一次等待一条连接（一个窗口五条）。`Changes` 只回答「剪贴板有没有变」，**「变了算不算 copy」在监听**——
那要问「手上是哪一段」，只有监听知道。

**「同一段再来一次」算不算新 copy：问过用户确认**（2026-10-10）。规则是两条，都写在 `Watch::run` 的
`Arrived` 分支上：

- **重开窗口只由「与手上不同的 reading」触发**。真实会话里每次等待都新开连接、每条连接都先报水位，把重复报
  当成新 copy 去重开窗口，会让静止的剪贴板永远攒不满窗口，一个面板都弹不出来。
- **但「面板弹过又关掉之后，同样的词再复制一次」算新 copy**——由 `armed` 位区分：开面板就是放下这个位。

两条合起来的效果：`arm("A") → 静默一个窗口 → copies("B")×5（之间没有窗口关闭）→ 静默一个窗口` 只弹
**一个**面板。

**正文读取有 2 秒上限**（`READ_TIMEOUT`）：读 offer 是向**选中内容的属主**要数据，协议不保证它回答，而这段
阻塞正好压在「面板 spawn 之前」和「停止通道被检查之前」。超时的读**被丢弃而不是被杀掉**（线程自己等属主关管道），
代价是每个卡住的属主留一条线程——这一条写在代码里，不假装没有。

**`window.rs` 里监听先于 webview 启动、且在自己的线程上**：一个死活不松剪贴板的会话不该变成「窗口永远打不开」；
`--watch` 也是一次开窗，两个都要成立。

## 给下游的交接

- **tickets/17（加固）**：真机清单里新增的「复制自动弹（`--watch`）」一节（`docs/desktop-manual-checks.md`）
  全部未在真 niri 上走过：连复制三次只弹一个面板、✕ 关掉后复制同一段再弹（命中缓存）、`wl-copy --sensitive`
  的拒绝态、关开关后监听自退、不带 `--watch` 的启动让监听退出、窗口开着时再 `--watch` 开始监听、
  GNOME 下 `--watch` 不启监听。`sway`/无会话下 `Changes::open()` 失败只会在 stderr 留一行，没有界面可挂。
- **真机上一件必须验的事**：`Changes::change` 的「水位 vs 变化」判断只能在有真剪贴板的地方验——
  假 `Observer` 挡不住这类错误（这一条已经用掉了四轮 review：三次都是这条路径上的真 bug）。真机上
  按 17 的清单走一遍，重点看「复制一段普通文本后面板真的弹出来」。
- **`--watch` 的常驻承诺**：默认路径（不带 `--watch`）下监听线程不启动，这一点由 `Mode` 与
  `window.rs` 的 `match` 保证，测试只覆盖到 `Desktop`/`Watch` 这一层；「真机上没有 `--watch` 就没有多余线程」
  属于 17 的目测项。
- **面板的 `activate` 复用没有改动**：监听 spawn 的是一模一样的 `plainly-panel --clipboard`，所以「第二次
  activate 复用并重读剪贴板」这条语义是票据 13/15 的，不是这里的；这里只保证「一次 burst 只 spawn 一次」。

## 已知取舍

- **`--watch` 是一个独立启动，不是一个开关效果**：`copy_auto_popup = true` 只写文件，不会拉起任何进程；
  监听得由键绑 / 桌面自启动拉起，而且它读开关。这是规格 §12 补定的「开关打开时由 `plainly-desktop` 承担」
  ——把「谁拉起它」留给环境是刻意的，因为窗口替用户 spawn 进程会破坏「默认路径下没有东西需要常驻」。
- **`kill -9` 之后不会自愈**：没有任何守护、没有重启循环。开关还是 `true`，但监听不在了——这正是
  「它读开关」换来的：重启的监听不会绕过「关掉就停」。
- **settle 窗口是数出来的，不是量出来的**（每片 50ms，五片一个窗口）。这样测试不用真的等 250ms，
  代价是窗口长度与 `POLL` 绑在一起：改 `POLL` 会改窗口的粒度，`WINDOW` 常量在测试里跟着算。
- **`--watch` 仍然需要一次真实剪贴板**：没有会话时 `Changes::open()` 报错，窗口照开、监听不启动，
  stderr 一行英文（库的句子）。
- **监听每次等待都新建一条 Wayland 连接**：一个 settle 窗口五片、每片一条，一次复制约十几条连接。
  这是「被取消的 watcher 不能复用」的直接代价；换来的是没有任何一条 stale cancellation 会落到下一次等待上
  （守时线程持有的是那一次等待自己的 `CancelHandle`，等待结束后它就被 join 掉了）。
- **重复的读取会多读一次正文**：监听读一遍、面板再读一遍。这是「监听不判定任何东西」的代价，
  也是自动触发与键绑同路径的原因。面板的读取本来就发生在它自己的进程里。
