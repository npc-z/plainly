# 09 提示词参数化与版本迁移

Type: grilling
Status: resolved
Blocked by: 01

## Question

定下**"提示词即数据"**的模型——护城河是这份契约，所以它必须可调，而不是硬编码。

- 可调项：等级（A1–C1+）、母语、输出小节开关、自定义系统提示。
- 存储与合并：默认提示词、用户覆盖、片段（如"只保留学术词汇"）如何组合；用户改了之后 schema 还成不成立。
- **版本绑定与迁移**：提示词版本与 `schema_version` 绑定；历史记录用**旧版本渲染**还是**用新提示词重跑**（这是两条不同的产品语义，要明确选一条）。
- 兜底：用户把提示词改坏、schema 校验持续失败时的行为。

输入：原型 `SKILL.md`（默认提示词的迁移来源）、票据 01 的 schema、Q8 的决定。

## Comments

- **来自票据 01 的两个版本号**：`artifact_version`（数据模型，随记录入库）与 `prompt_version`（产出它的提示词）。两者**独立演化**——迁移检查必须能分开判断"是数据模型变了"还是"只是措辞变了"。
- **从雾区并进来的问题**：Level（以及 Native Language）是应用的设置（01 已定），但**用户改了 Level 之后，旧 Record 跟着重跑还是保持原样**？这与"旧记录用旧提示词渲染还是用新提示词重跑"是同一个迁移语义问题，在本票据内一并决定。
- 票据 01 已 resolved，**本票据的阻塞已解除**。
- **与票据 15 的边界（精确版，2026-10-05）**：等级、母语、输出小节开关、自定义系统提示的**值**存放在配置文件的 `[app]` / `[prompts]` 段（**15 的地盘**：文件格式、位置、原子写、密钥），但**它们的含义、默认值、如何喂进提示词、以及版本与迁移归本票据**。两边不要互相越界：15 不定义参数语义，09 不改配置文件格式。
- **一处必须与它保持一致的机制**：每条 Record 会**盖上"当时用的"等级与母语**（票据 01 定的"应用附加元数据" + 票据 08 的入库）。这是"改设置不会改变旧记录"能成立的原因。所以本票据那条悬着的问题——"用户改了 Level，旧 Record 跟着重跑还是保持原样"——的答案必须与它一致，或者明确推翻它。
- **一条硬纪律（票据 08 的幂等键直接依赖它）**：`prompt_version` **内容改了就必须升版本**。票据 08 的 `lookup_key` 含 `prompt_version` 而不含提示词正文，所以"改了提示词但没升版本"会导致**旧答案被持续命中**——用户以为换了提示词，实际拿到的还是旧的。这条升级纪律是本票据必须交付的一部分，不是附带要求。

## Answer

五条决策 + 三组实测，2026-10-05 全部按推荐采纳。

### 先说实测（决策都建在它上面）

出厂提示词只有**两个参数位**：`{{LEVEL}}`（两次）、`{{NATIVE}}`（两次）。测试条件：deepseek-flash、关思考、temperature 0、4 段跨语域（p02 习语 / p04 文学 / p06 法律 / p12 正式），共 24 次请求，六次运行契约全 4/4。全部数据在 `bench/results/deepseek/`，汇总在 `bench/FINDINGS.md`。

| | 等级坍缩成逐字相同的相邻对 | 平均词长 A2/B2/C1 | 与原文平均相似度 A2/B2/C1 |
|---|---|---|---|
| **只发标签** | **3 / 8** | 4.29 / 4.27 / 4.26 | 0.460 / 0.475 / 0.463 |
| **标签 + 描述** | **1 / 8** | **4.05** / 4.32 / 4.29 | **0.395** / 0.463 / 0.462 |

- **母语是强参数**：`BENCH_NATIVE=Japanese` 时四段翻译全部切成日语（43–49 个假名/汉字），而 `comprehensible` 与**每一条 gloss 全部保持英文**（4/4）。产品承诺"用英语解释英语"不会被母语设置污染——**值得验的是 gloss 会不会泄漏，不是翻译会不会切换**。
- **等级是弱而粗的参数，而且不发描述就等于没发**：只发标签时两个等级在三段上产出**逐字相同**的文本；把描述内联后 A2 被分离出来（词长 4.29→4.05、与原文相似度 0.460→0.395，即改写更彻底）。
- **B2 与 C1 仍无法区分**（4.32 vs 4.29；0.463 vs 0.462）。机制很可能是**契约内部自相矛盾**：C1 的描述是"keep most of the original structure"，而提示词自己的硬规则是"never return the passage unchanged"——**后者赢了**。
- 连 A2 也不可靠地最简：p06 与 p12 上它的平均词长是三档里**最高**的。
- 口径：4 段 × 1 模型 × 每条件一次。temperature 0 使每行可复现，且"两个等级产出逐字节相同"不是采样噪声；但方向是**倾向**而非定律。结论不是"等级没用"，而是**"等级是提示、不是契约，且必须带着描述一起发"**。

### 1. 可调项

- **结构化参数只有两个**：**等级**与**母语**（都进 `lookup_key`，票据 08）。
- **等级必须连含义一起发**，不能只发标签——依据见上。
- **输出小节开关 = 显示层开关**：提示词照旧请求全部四个键，开关只控制**显示**。理由：改 schema 形状会让**每个开关组合变成一个 artifact 版本**，成本远超收益；而 `grammar` 本就 nullable、翻译很短。代价是"为隐藏的小节付几个 token"，换来的是**不碎片化缓存、切换即时、不必重新生成**。因此开关属于 `[app]` 的**显示偏好**，**不进 `lookup_key`**。
- **不做**：片段注册表（"只保留学术词汇"就是用户写在附录里的一行）、按小节的 schema 变体、UI 内多套提示词管理。

### 2. 存储与合并：出厂默认 + 用户附录（append-only）

- 出厂默认**不可变、随版本更新**（v6→v7→…）；用户的**附录**追加在它后面；合并结果即**有效提示词**。
- 理由有据：这份契约**被反复调过**（v1→v6，六个变体）。整份拷贝会让**上游每次改进都到不了用户手里**，而且容易被改坏那四个 JSON 键名——**契约就靠那几个键名**。附录让上游改进自动到达、用户改动不丢。
- **局限（诚实记下）**：附录**只能加、不能删**基础规则。这是有意的——**对一个契约来说，增加比删除安全**：基础保持 artifact 的定义，否则各人的历史就不再可比。想删规则的人只能写一句相反的规则去覆盖它；这确实是弱一点的能力，记进规格而不是假装不存在。

### 3. 版本 = 有效提示词的内容哈希（派生，不是人声明的）

**这是本票据最有价值的一条**：票据 08 那条硬纪律"**内容改了就必须升版本**"从**纪律**变成**结构保证**——它不可能再被违反。

- **哈希覆盖什么（比提问时的说法更严）**：`SHA-256(出厂默认 + 用户附录 + 等级描述表)`，**占位符不替换**。
  - **为什么必须带上等级描述表**：如果描述表是应用侧的代码而不是提示词数据，那么"改一句描述"会改变模型输出、却不改变版本 → 正好制造票据 08 要防的那种**陈旧命中**。把描述表算作提示词数据，这个洞就堵上了。**描述表的措辞归本票据（即提示词），归 16 的只是把等级与含义显示出来。**
  - **为什么占位符不替换**：等级与母语**已经是 `lookup_key` 的独立分量**，替换进哈希只是重复。
- 记录里**同时存人类可读标签**（`v6-synthesis`）：哈希是"真的版本"，标签是"给人的名字"。
- **代价（诚实记下）**：应用更新改动了出厂提示词 → 所有段落 hash 变化 → **每段下次查询各重新生成一次**。这是**正确**行为（提示词变了，答案就该变），但要写明：**历史里同一段落可能同时存在多个 prompt 版本的记录**——这是特性（可比较），代价是 UI 要能按版本区分（归 16）。

### 4. 迁移语义：旧记录原样渲染，重跑只能显式

- 与票据 08"Record 盖上当时的值"一致——这也正是它那条悬着问题的答案：**改 Level 不触碰旧记录**；同一段落在新等级下是**新查询**（新 key → 新记录）。
- 记录存 hash + 标签、**不存提示词正文** → 旧记录永远可渲染，不必永久保留旧提示词版本。
- `artifact_version` 与 `prompt_version` **独立演化**（票据 01）：只要渲染器还能读该 artifact 版本，就原样渲染。v0 只有一个 artifact 版本，这条是留给未来的门。
- **明确否掉**"用新提示词静默重跑全部历史"：既花钱、又销毁旧答案，且与"改设置不改变旧记录"直接冲突。

### 5. 兜底：绝不静默回退

- 契约失败（走完票据 04 的重试之后）→ 明说"**你的提示词没通过契约**"，并给一键"**改用出厂默认重试**"；**记录里记的是真正产出它的那个提示词**。
- **不做保存期探针**（一次可能因 429 而误报的调用），也**不在保存时阻断**（改提示词要便宜）。失败应当暴露在**真正失败的那次查询**上——那时才有真实上下文。

### 一条连带要求：出厂的 v6 要变成 v7

本票据要求"等级必须连含义一起发"，而 **v6-synthesis 只发标签**。所以出厂提示词要更新为**内联等级描述表**的版本（已在票据 14 上记一条）。这不是措辞微调——实测显示它决定这个旋钮有没有效果。

### 给下游

- **票据 16**：设置页显示等级**及其含义**；提示词附录的编辑器；历史要能**按 prompt 版本区分**同一段落的多条记录。
- **票据 08**：`prompt_version` 现在是**内容哈希（派生）**，记录另存人类标签；同一段落可以有多个版本的记录。
- **票据 15**：**附录与等级描述表属于 `[prompts]`**（提示词数据），**等级/母语的值属于 `[app]`**（人的选择）。
- **票据 14**：出厂提示词需升级到内联等级描述表的版本。
